## 0. 한눈에 보는 요약

DSA 교육 콘텐츠 관리 플랫폼은 사내 강사가 구글 슬라이드로 만든 강의 교안을
**수강생에게는 편집·다운로드 없이 목차와 함께 열람**시키고, 강사에게는
**배포·실시간 설문·AI 기반 문제/질문/평가 생성**을 지원하는 시스템이다.

- **개발 방식**: 별도 서버·DB를 새로 구축하지 않고 Google Workspace(Apps
  Script, Drive, Slides, Sheets) 자원을 최대한 활용해 가볍게 개발했다.
- **시스템 구성**: 독립형 Google Apps Script(GAS) 프로젝트 4개(그중 1개는
  구현 예정) + AI 전용 API 서버(Cloud Run) 1개 + 데이터 저장소 3종(Drive
  JSON 파일, Google Sheets, Supabase PostgreSQL).
- **AI 활용 지점**: 시험문제 생성, 실시간 설문 의견 요약, 가상 학생질문 생성,
  강의자료 평가(+웹검색 기반 최신성 검토) 4개 기능. 전부 OpenAI(GPT-4o)
  하나로 통일되어 있고, 전용 백엔드(ai-server)를 통해서만 호출된다.

## 1. 전체 아키텍처 설명 (구조도 생성용)

### 1.1 구성요소 목록 (구조도의 "박스")

**사용자**
- 강사(사내 전 직원, 조직 계정 로그인 필요)
- 수강생(로그인 불필요, 익명 접속)
- 관리자(sypark@datasa.net — 공유 드라이브 관리자 권한 보유, 배포·설정 담당)

**애플리케이션 계층 — 독립형 GAS 프로젝트 4개(별도 clasp 프로젝트, 별도 배포)**

| 프로젝트 | 성격 | 실행 계정(executeAs) | 접근 대상(access) | 역할 |
|---|---|---|---|---|
| `publish-engine` | GAS **라이브러리**(웹앱 아님) | 호출자(다른 프로젝트) 권한으로 실행 | — | 슬라이드ID 추출, 슬라이드 공유설정, 목차/본문 추출, Drive·Sheets·Supabase 기록의 "엔진" 역할. 다른 3개 프로젝트가 라이브러리로 가져다 씀 |
| `system-a-viewer` | 웹앱(공개) | `USER_DEPLOYING`(관리자) | `ANYONE_ANONYMOUS`(전체 공개) | 수강생용 뷰어. `?k=키워드`로 접속, 목차+슬라이드 embed, 실시간 설문 응답 |
| `system-b-dashboard` | 웹앱(사내) | `USER_ACCESSING`(접속자 본인) | `DOMAIN`(조직 내부) | 강사용 대시보드. 배포/수정/삭제, 실시간 설문 출제, AI 기능 4종 호출 |
| `system-c-excel` | (미착수) | `USER_ACCESSING` 예정 | `DOMAIN` 예정 | 취업/연수생 엑셀 데이터 분석·보고서화(별도 대시보드) |

**AI 백엔드 — ai-server (Cloud Run, Python)**
- FastAPI 서버 1개. system-b-dashboard가 `UrlFetchApp`으로만 호출(공유 비밀키
  `AI_SERVER_KEY`를 `X-API-Key` 헤더로 인증).
- 엔드포인트 4개: `/exam-questions`, `/opinion-summary`, `/virtual-questions`,
  `/lecture-evaluation` (+ 헬스체크 `GET /`).
- 내부에서 LangChain/LangGraph로 OpenAI(GPT-4o)를 호출하고, 필요 시 Supabase를
  직접(REST/PostgREST) 조회한다.

**외부 서비스/저장소**
- Google Drive: 강의 원본 슬라이드 파일(공유 드라이브), 목차데이터 폴더(`키워드.json`)
- Google Sheets: 강의 메타데이터 DB(시트명 `강의목록`)
- Supabase (PostgreSQL, PostgREST): 실시간 설문 라이브 데이터·영구 결과, 슬라이드
  본문 텍스트 스냅샷, 가상질문 페르소나 정의·결과, 강의자료 평가 결과
- OpenAI API: GPT-4o(LangChain `ChatOpenAI`) + Responses API 기반 내장 웹검색
  도구(`web_search_preview`)

### 1.2 데이터 저장 3원화 (구조도에 저장소 3개로 표시)

| 데이터 | 위치 | 형식/성격 |
|---|---|---|
| 교안 메타(키워드·제목·슬라이드ID·게시URL·목차JSON링크·최종수정) | Google Sheets(`강의목록` 시트) | 키워드가 고유 키인 행 단위 데이터 |
| 목차(TOC) | Drive "목차데이터" 폴더의 `키워드.json` | 뷰어가 유일하게 읽는 소스. 강의 교체 시 덮어쓰기(스냅샷) |
| 슬라이드 본문 텍스트, 실시간 설문(임시/영구), 가상질문 페르소나·결과, 강의자료 평가 결과 | Supabase PostgreSQL | 테이블 단위. AI 기능의 근거 데이터이자 결과 캐시 |

### 1.3 핵심 시퀀스 A — 강의 배포 워크플로 (강사 → 학생)

```
강사 → (PPT를 공유 드라이브에 업로드 → "Google Slides로 저장")
강사 → system-b-dashboard 접속(사내 로그인) → 키워드+제목+슬라이드URL 입력 → [배포] 클릭
system-b-dashboard(Code.js) → google.script.run → publish-engine.publishLecture(url, keyword, title, tocMethod) 호출
  publish-engine 내부 처리 순서:
   1) URL에서 슬라이드ID 추출(정규식)
   2) 실제 파일이 Google Slides mimeType인지 확인(PPT를 그냥 연 것이면 에러로 안내)
   3) DriveApp으로 슬라이드 공유범위를 "링크가 있는 사용자 - 보기"로 변경
   4) SlidesApp으로 목차(제목만/첫텍스트) 추출
   5) Drive "목차데이터" 폴더에 {keyword}.json 저장(있으면 덮어쓰기)
   6) Google Sheets "강의목록" 시트에 키워드 기준 upsert
   7) 슬라이드 전체 텍스트를 추출해 Supabase slide_contents에 저장(기존 행 삭제 후 재삽입)
system-b-dashboard ← 결과(뷰어 URL: system-a-viewer URL + "?k=" + 키워드) 수신 → 화면에 강의 목록 갱신
강사 → 학생 게시판 등에 뷰어 URL 공유
학생 → system-a-viewer?k=키워드 접속(로그인 불필요)
  system-a-viewer(Code.js doGet) → publish-engine.getTocData(keyword) 호출(단 하나의 데이터 통로)
  → 목차데이터 폴더의 {keyword}.json을 그대로 읽어 반환
  → Portal.html이 좌측 목차 사이드바 + 우측 슬라이드 iframe embed로 렌더링
```

같은 키워드로 재배포하면 URL은 그대로 두고 내용만 갱신된다(뷰어 주소 영구 고정
원칙). URL 없이 제목만 바꾸는 경량 경로(`updateLectureTitle`)도 별도로 있다.

### 1.4 핵심 시퀀스 B — 실시간 설문 (강사 ↔ Supabase ↔ 학생, 서로 다른 GAS 배포 간 상태 공유)

```
[출제] 강사(system-b-dashboard) → 문제유형/질문/선택지/정답 입력 → [학생들에게 공개]
  → publish-engine.Survey.js → Supabase REST API(POST survey_temp_questions)
  → 24시간 지난 미완료 설문 자동 정리(cleanupStaleSurveys_) 후, 고유키(영소문자+숫자 4자리,
    o/l/0/1 제외) 발급 → 강사 화면에 고유키 표시

[응답] 학생(system-a-viewer) → [답변하기] → 고유키 입력
  → system-a-viewer.Code.js getSurveyQuestion() → publish-engine.getSurveyByAccessKey()
  → Supabase에서 access_key + status='active' 조회 → 문제 표시
  → 학생 답변 제출 → submitSurveyAnswer() → Supabase RPC submit_survey_answer()
    (문제가 여전히 active일 때만 원자적으로 INSERT, 강사가 그 순간 종료해도 경쟁상태 없음)

[종료·집계] 강사 → [설문종료]
  → 객관식/단답형: GAS 코드 내부에서 직접 채점·정답률·분포 계산
  → 의견형: system-b-dashboard.Code.js summarizeOpinions_() → ai-server POST /opinion-summary
    → LangChain(OpenAI gpt-4o)로 요약 생성 → 실패 시 null(학생 답변 원문을 그대로 표시)
  → 이 시점엔 결과 화면만 뜨고 아직 저장되지 않음

[저장 선택] 강사가 [설문결과 저장] 또는 [저장하지 않고 종료] 중 하나를 선택해야 창이 닫힘
  → 저장: Supabase RPC finalize_survey() (한 트랜잭션으로 survey_results INSERT + 
    survey_temp_questions/answers DELETE)
  → 미저장: survey_temp_questions DELETE만 수행, 결과 어디에도 안 남음
```

핵심 포인트: 대시보드(system-b)와 뷰어(system-a)는 **서로 다른 GAS 배포**라
`CacheService`를 공유할 수 없다. 그래서 진행 중 상태를 GAS가 아니라 **Supabase를
공유 상태 저장소**로 사용해 두 웹앱이 간접적으로 통신한다.

### 1.5 핵심 시퀀스 C — AI 기능 공통 호출 패턴 (4개 기능 공통 골격)

```
강사(system-b-dashboard) → [AI 기능] 버튼 클릭
  → 클라이언트: checkAiEnabled_() 로 서버의 isAiEnabled() 확인(AI_MODE 스크립트 속성)
  → OFF면: ai-server 호출 자체를 하지 않고 "AI 크레딧이 필요합니다" 모달만 표시
  → ON이면: google.script.run으로 generate***() 함수 호출
    → system-b-dashboard.Code.js가 UrlFetchApp으로 ai-server POST /{endpoint} 호출
      (헤더: X-API-Key: AI_SERVER_KEY)
    → ai-server: auth.verify_api_key() 로 키 검증
    → ai-server: supabase_client.py로 필요한 데이터 조회(슬라이드 본문/설문결과/가상질문 등)
    → ai-server: chains/*.py의 LangChain(+LangGraph) 체인 실행 → OpenAI 호출
    → 결과를 GAS로 반환 → GAS가 성공 시 결과를 publish-engine 경유로 Supabase에 캐시 저장
  → 실패(오류/타임아웃/쿼터 등 원인 불문): 화면에는 "현재 AI 기능을 사용할 수 없습니다"
    같은 고정 문구만 노출, 원인은 로그(GAS Logger.log / ai-server 서버 로그)로만 남김
    (의견 요약만 예외 — 실패해도 학생 답변 원문은 항상 보여줌)
```

4개 기능 각각의 구체 차이:

| 기능 | LangChain 구조 | 참고 데이터 | 결과 표시 위치 | 캐시 정책 |
|---|---|---|---|---|
| 시험문제 생성 | 구조화 출력(`with_structured_output`) 단발 체인 | 슬라이드 본문 + (레벨 매칭되는) 가상질문 | 새 탭(팝업) | 캐시 없음(매번 생성) |
| 의견 요약 | 단발 체인(프롬프트만) | 학생 답변 원문 결합 | 결과 모달 | 캐시 없음(설문 1회성) |
| 가상질문 생성 | **LangGraph** 상태 유지형 순차 루프 | 슬라이드 본문(Part1~3 분할) | 새 탭(팝업) | 키워드+페르소나당 최신 1건 |
| 강의자료 평가 | 구조화 출력 1회 + 웹검색 2단계(조사→재작성) | 슬라이드 본문 + 설문 결과 + 가상질문 | 결과 모달(산문형 리포트) | 키워드당 최신 1건 |

### 1.6 핵심 시퀀스 D — 가상질문 생성 (LangGraph 그래프 구조, 구조도의 서브 다이어그램)

```
[상태(State)] persona_prompt, batches(Part1~3), batch_index, use_summary,
              context_text/context_summaries(누적 컨텍스트), all_questions, final_questions

START → read_batch 노드
          - 이번 구간(Part N) 슬라이드 텍스트 + 지금까지의 컨텍스트를 프롬프트에 담아
            OpenAI 구조화 출력 호출 → {questions, batch_summary} 획득
          - 슬라이드 50장 이하: 지나온 구간 "원문"을 그대로 누적
          - 슬라이드 50장 초과: 원문 대신 "구간 요약(batch_summary)"만 누적(토큰 절약)
        ↓ 조건부 엣지(_route_after_batch)
        batch_index < 전체 구간 수 → read_batch로 되돌아감(반복)
        batch_index == 전체 구간 수 → filter_questions로 진행
                                              ↓
                                       filter_questions 노드
                                         - 전체 구간에서 모인 질문을 한 번에 놓고
                                           중복/유사 질문을 정리한 "최종본"만 생성
                                              ↓
                                             END
```

"질문 없음"도 정상 결과로 취급(의미 있는 내용이 없거나 이미 다룬 내용과 겹치면
억지로 만들지 않음). 페르소나는 코드가 아니라 Supabase
`virtual_question_personas` 테이블의 데이터로 관리되어, 새 페르소나 추가 시
코드 변경이 필요 없다.

### 1.7 핵심 시퀀스 E — 강의자료 평가 (웹검색 2단계 분리, 실패 격리 구조)

```
generate(slide_count, slide_text, survey_rows, persona_groups)
  ① evidence_basis = build_evidence_basis(...)   ← LLM 아님. 코드가 조회 결과 개수를 직접 조립
  ② core = _generate_core(...)                    ← 구조화 출력 1회
       - structure_review (항상 생성)
       - learner_signal_review (실시간설문·가상질문 있을 때만, 없으면 null)
       - suggestions, data_coverage
  ③ currency_review = _generate_currency_review(core.structure_review)  ← 완전 부가 기능
       내부(항상 예외를 던지지 않도록 최상위 try/except로 감쌈):
         a) _run_web_search(topic_summary)
            - get_web_search_llm(): Responses API + web_search_preview 도구 바인딩
            - ThreadPoolExecutor + future.result(timeout=25초)로 하드 타임아웃
            - TPM(분당 토큰) 레이트리밋(429) 시 3초 대기 후 1회 재시도
            - 특이사항 없으면 "NONE" → None 반환
         b) _rewrite_currency_review(topic_summary, raw)
            - 검색 도구 없는 일반 호출로 원시 결과를 한국어 요약 의견으로 재작성
            - 마크다운 링크 잔여물은 정규식으로 한 번 더 제거(안전망)
  ④ 네 값을 합쳐 dict 반환 → lecture_evaluations 테이블에 upsert 저장(키워드당 1건)
```

### 1.8 권한/보안 관련 흐름 (구조도의 "인증" 레이어)

- **GAS 프로젝트 간**: `system-a-viewer`/`system-b-dashboard` → `publish-engine`은
  GAS **라이브러리 호출**(같은 실행 컨텍스트, API 키 없음).단, 라이브러리 코드는
  "호출자(현재 로그인한 사용자)의 Drive 권한"으로 실행된다는 제약이 있다(공유
  드라이브 관리자 권한이 필요한 동작은 배포자 계정 권한에 의존).
- **GAS ↔ ai-server**: `UrlFetchApp` + `X-API-Key: AI_SERVER_KEY`(공유 비밀키,
  스크립트 속성/Cloud Run 환경변수 양쪽에 동일 값 등록).
- **ai-server ↔ Supabase**: `service_role` 키로 REST 직접 호출(RLS는 모든 테이블에
  걸려 있지만 service_role은 우회 — anon/authenticated 키 유출 대비용 방어선).
- **ai-server ↔ OpenAI**: `OPENAI_KEY`(Cloud Run 환경변수 전용, GAS 스크립트 속성에는
  존재하지 않음 — 모델 제공자 키는 전부 ai-server에만 둔다는 정책).
- **설정값 관리**: 모든 ID/URL/키는 `publish-engine/Config.js`의
  `PropertiesService`(스크립트 속성)에 모아두고, `getSetting()`/`getSecret()`으로
  다른 프로젝트가 가져다 씀(하드코딩 금지, 계정 이전 시 이 한 곳만 교체).

## 2. 코드 상세 설명

### 2.1 publish-engine (게시엔진, GAS 라이브러리)

다른 3개 시스템이 공유하는 "엔진" 계층. 웹앱이 아니라 **GAS 라이브러리**로만
동작하며, 파일 6개로 구성된다.

- **`Config.js`** — 중앙 설정 허브. `PUBLIC_KEYS`(공용, 아무 키나 조회 가능)와
  `SECRET_KEYS`(민감, `getSecret()`으로 화이트리스트 검증 후에만 반환)를
  분리해 관리. `checkSettings()`로 편집기에서 등록 상태를 육안 점검 가능.
- **`SlideParser.js`** — 슬라이드 URL에서 ID 추출(`extractSlideId`, 정규식),
  목차 추출(`extractSlideToc`, TITLE/CENTERED_TITLE 플레이스홀더 또는 첫
  텍스트 도형 중 선택 가능), 슬라이드 본문 전체 텍스트 추출
  (`extractSlideContents`, AI 기능용 원문). 제목 없는 슬라이드는 목차에서
  제외하되 원래 슬라이드 위치(`index`)는 유지(재번호 없음).
- **`Publish.js`** — 배포 핵심 로직의 진입점.
  - `publishLecture()`: mimeType 검증(PPT를 "슬라이드로 저장" 안 했으면 원인을
    안내하는 에러) → 공유설정 → 목차추출 → JSON저장 → 시트기록 → 슬라이드
    본문 Supabase 저장까지 한 번에 처리.
  - `updateLectureTitle()`: 슬라이드 재추출 없이 제목만 갱신하는 경량 경로.
  - `unpublishLecture()`: 슬라이드 공유를 PRIVATE로 되돌리되, **같은 슬라이드를
    다른 키워드가 아직 참조 중이면 공유 설정은 건드리지 않음**(다른 키워드의
    뷰어가 함께 깨지는 걸 방지) + 설문/슬라이드본문/가상질문/강의자료평가 등
    관련 Supabase 데이터 전부 정리.
  - `getDbColumnIndexes()`: 시트 헤더를 이름으로 찾되 못 찾으면 고정 열 순서로
    대체하는 방어적 헬퍼(헤더 오탈자에도 안전) — 컬럼 인덱스가 필요한 모든
    코드가 `header.indexOf()`를 직접 쓰지 않고 이 함수를 거치도록 강제.
  - `getTocData()`: 뷰어(system-a)가 데이터를 가져오는 유일한 통로.
- **`SlideContent.js`** — 슬라이드 본문을 Supabase `slide_contents`에 스냅샷
  형태로 저장/삭제(재배포 시 기존 행 삭제 후 재삽입).
- **`Survey.js`** — 실시간 설문의 Supabase REST 클라이언트 겸 비즈니스 로직
  (고유키 발급, 방치 설문 정리, 채점, RPC 호출).
- **`VirtualQuestion.js`**, **`LectureEvaluation.js`** — 각각 가상질문/강의자료
  평가 결과의 Supabase 캐시 조회·저장·삭제 다리 역할(ai-server 호출은
  system-b가 하고, 결과 캐시 저장만 이 라이브러리가 담당).

### 2.2 system-a-viewer (수강생 뷰어)

- **`Code.js`**: `doGet(e)` 하나가 전체 화면 진입점. `?k=` 파라미터 → `getTocData()`
  단 하나의 호출로 제목/슬라이드ID/목차를 받아 `Portal.html` 템플릿에 주입.
  키워드 없음/못 찾음/내부 오류 3가지 케이스 모두 **고정 문구**만 반환하고,
  특히 "못 찾음" 케이스는 사용자가 입력한 키워드 원문을 응답에 절대 포함하지
  않는다(보안 정책, 아래 4장 참고). 실시간 설문 응답용 `getSurveyQuestion()`/
  `submitSurveyAnswer()`도 여기서 얇은 다리 역할만 한다.
- **`Portal.html`/`Sidebar.html`**: 좌측 목차(검색 가능) + 우측 슬라이드
  iframe embed. 목차 클릭 시 `objectId` 기반으로 슬라이드 이동. 목차 JSON을
  `<script>`에 주입할 때 `</script` 조기 종료를 막기 위해 `<`를 이스케이프.

### 2.3 system-b-dashboard (강사 대시보드)

- **`Code.js`**: `doGet(e)`가 `?page=help` 여부로 `Dashboard.html`/`Help.html`
  분기. `getLectureList()`가 `PublishEngine.getPublicConfig()`로 설정을 받아
  강의 목록을 조회. AI 4종 기능의 GAS 쪽 진입점(`generateExamQuestions()`,
  `summarizeOpinions_()`, `generateVirtualQuestions()`,
  `generateLectureEvaluation()`)이 전부 이 파일에 있고, 공통적으로
  `checkAiEnabled_()` 게이트 → `UrlFetchApp`으로 ai-server 호출 → 실패는
  `{error:true}`로 흡수하는 패턴을 따른다.
- **`Dashboard.html`**: 목록 표(URL복사/뷰어열기 아이콘 버튼) + 배포/수정/삭제
  모달 + 실시간 설문 출제·결과 모달 + AI 기능 4종의 옵션 선택·결과 표시
  모달. 사용자 입력을 화면에 넣기 전 항상 통과시키는 `esc()` 이스케이프
  함수를 재사용(XSS 방지 공통 패턴). AI 결과가 긴 경우(시험문제·가상질문)는
  팝업 차단을 피하기 위해 "결과 모달을 먼저 띄우고 그 안에서 새 탭을
  자동으로 여는" 패턴(`openExamResultWindow`/`openVqResultWindow`)을 쓴다.
- **`Help.html`**: 기능별 사용법 안내 페이지(정적 콘텐츠).

### 2.4 ai-server (Python, FastAPI + LangChain + LangGraph, Cloud Run)

- **`main.py`**: FastAPI 앱 진입점. 4개 POST 엔드포인트 + 헬스체크 `GET /`.
  각 엔드포인트는 (1) `verify_api_key()`로 인증 → (2) `supabase_client.py`로
  필요한 원본 데이터 조회 → (3) `chains/*.py`의 함수 1개 호출 → (4) 결과를
  JSON으로 반환, 이라는 동일한 4단계 골격을 따른다. Pydantic `BaseModel`로
  요청 스키마를 강제한다.
- **`auth.py`**: 공유 비밀키 검증 한 함수(`verify_api_key`). AI_MODE 여부는
  이미 GAS 쪽에서 걸러졌다는 전제하에, 여기서는 "GAS만 호출 가능한가"만 확인.
- **`llm_provider.py`**: LangChain `ChatOpenAI` 인스턴스 생성을 한 곳에 모은
  공용 모듈. `get_openai_llm()`(일반 호출용)과 `get_web_search_llm()`(Responses
  API + `web_search_preview` 도구 바인딩, 강의자료 평가 전용)으로 분리.
  모델명은 `OPENAI_MODEL` 환경변수로 코드 변경 없이 교체 가능(기본값 `gpt-4o`).
- **`supabase_client.py`**: PostgREST 읽기 전용 클라이언트. 슬라이드 본문
  (`get_slide_segments`), 페르소나(`get_persona`), 레벨 매칭 가상질문
  (`get_virtual_questions`), 설문 결과(`get_survey_results`), 페르소나별
  전체 가상질문(`get_virtual_questions_by_persona`, "학생N(이름)" 라벨을
  여기서 계산해 붙임)을 제공.
- **`chains/exam_generator.py`**: 시험문제 생성. `with_structured_output`으로
  `ExamQuestionList` Pydantic 모델을 직접 받아 파싱 실패 위험을 없앰. 문제
  유형(객관식/단답형/서술형) × 난이도(초/중/고) 조합별 프롬프트 지시문을
  딕셔너리로 관리하고, 레벨에 매칭되는 가상질문이 있으면 "참고자료" 섹션으로
  프롬프트에 추가.
- **`chains/opinion_summarizer.py`**: 의견형 설문 요약. 단일 프롬프트 호출.
  hallucination 방지 규칙(숫자 언급 금지, 없는 내용 추측 금지, 다수/소수
  판단 기준 4단계)이 프롬프트에 상세히 명시되어 있다.
- **`chains/virtual_question_agent.py`**: 가상질문 생성. `langgraph.graph.
  StateGraph`로 구현된 유일한 "에이전트"형 체인(1.6절 참고). `TypedDict`
  기반 상태(`_VqState`)를 노드 간에 주고받는 전형적인 LangGraph 패턴.
- **`chains/lecture_evaluator.py`**: 강의자료 평가. 구조화 출력 1회(핵심
  평가) + 웹검색 도구를 쓰는 별도 호출(부가 기능, 완전 격리)로 구성. 근거
  명시(`evidence_basis`)는 LLM이 아니라 파이썬 코드가 직접 문자열로 조립.

### 2.5 Supabase 스키마 (`DB구조.sql`, 단일 소스)

| 테이블 | 성격 | 핵심 컬럼 |
|---|---|---|
| `survey_temp_questions` | 라이브(작업용) | access_key, lecture_keyword, question_type, status |
| `survey_temp_answers` | 라이브(작업용) | question_id(FK, cascade), answer_text |
| `survey_results` | 영구 | lecture_keyword, accuracy_rate, answer_distribution, opinion_summary/raw |
| `slide_contents` | 스냅샷(재배포 시 갱신) | lecture_keyword, slide_index, slide_text |
| `virtual_question_personas` | 정적 정의(데이터 기반) | persona_id, prompt, display_order, exam_level |
| `virtual_questions` | 스냅샷(키워드+페르소나당 1건) | questions(jsonb) |
| `lecture_evaluations` | 스냅샷(키워드당 1건) | evidence_basis, structure_review, currency_review, suggestions |

RPC 함수 2개(`submit_survey_answer`, `finalize_survey`)가 "조회 후 쓰기" 경쟁
상태를 트랜잭션으로 원자화한다 — 특히 `finalize_survey()`는 "결과 저장 +
작업 테이블 정리"를 한 트랜잭션으로 묶어 "작업 테이블에 남은 행 = 항상
미완료분"이라는 불변식을 보장한다.

## 4. 문제점과 해결 방안

개발·실기기 테스트 과정에서 확인된 제약과 그에 대한 대응 설계를 정리했다.
(발표 시 "문제 → 원인 → 해결"의 사례 연구로 활용 가능한 항목들)

### 4.1 보안 — 뷰어 키워드 파라미터 XSS
- **문제**: `?k=키워드`는 사용자가 URL에 직접 넣는 신뢰할 수 없는 값이다.
  "키워드를 찾을 수 없음" 같은 에러 메시지에 이 값을 그대로 이어붙이면
  입력값이 스크립트로 실행될 수 있다(초기 구현에서 실제로 확인된 취약점).
- **해결**: 키워드를 못 찾았을 때 **고정 문구만** 표시하도록 정책화(사용자
  입력을 절대 응답에 echo하지 않음). 그 외 사용자 입력을 화면에 표시해야
  하는 모든 곳에서 `esc()` 이스케이프 함수를 재사용, 목차 JSON을 `<script>`에
  주입할 때도 `</script` 조기 종료 방지 이스케이프 적용.

### 4.2 DB 시트 구조 변경에 대한 취약성
- **문제**: DB 시트는 사람이 직접 열어 편집할 수 있는 저장소라 헤더 문자열이
  언제든 바뀔 수 있다(실제로 B열이 "제목"이 아니라 "강의제목"으로 되어 있어
  스펙과 어긋난 적이 있다). 코드에서 `header.indexOf('제목')`처럼 이름을 직접
  찾으면 헤더가 바뀌거나 오탈자가 생기는 순간 조용히 깨진다.
- **해결**: `getDbColumnIndexes()` 공개 함수로 "이름으로 먼저 찾고, 못 찾으면
  고정 열 순서(A~F)로 대체"하는 방어적 조회 패턴을 도입하고, DB 시트 관련
  모든 코드(게시엔진·대시보드)가 이 함수만 거치도록 강제. 시트도 위치(첫
  탭)가 아니라 이름(`강의목록`)으로 찾아 탭 순서 변경에도 안전하게 함.

### 4.3 같은 슬라이드를 여러 키워드가 공유하는 경우의 배포 취소
- **문제**: 하나의 슬라이드 파일을 여러 키워드가 참조할 수 있는 구조인데,
  배포 취소 시 슬라이드 공유를 무조건 PRIVATE으로 되돌리면 그 슬라이드를
  쓰는 다른 키워드의 뷰어까지 함께 끊긴다.
- **해결**: `unpublishLecture()`가 삭제 전에 같은 슬라이드ID를 쓰는 다른
  키워드 행이 남아있는지 확인하고, 남아있으면 슬라이드 공유 설정은 건드리지
  않고 목차 JSON 삭제 + DB 행 삭제만 수행한다.

### 4.4 서로 다른 GAS 배포 간 상태 공유 불가
- **문제**: 실시간 설문의 "진행 중 문제·임시 답변"을 GAS `CacheService`로
  두려 했으나, 대시보드(system-b)와 뷰어(system-a)가 서로 다른 배포라
  캐시를 공유할 수 없었다.
- **해결**: 라이브 상태 저장소를 Supabase로 확정(작업용 테이블
  `survey_temp_questions`/`survey_temp_answers`). 정상 종료는
  `finalize_survey()` 트랜잭션으로 결과 이관 + 작업 테이블 삭제를 한 번에
  처리해 어정쩡한 중간 상태가 남지 않게 함.

### 4.5 새 탭 결과 화면이 팝업 차단으로 안 뜨는 문제
- **문제**: 옵션 입력 모달을 닫고 `google.script.run`의 비동기 콜백 안에서
  바로 `window.open()`을 호출했더니, 이 시점이 "사용자의 신뢰된 제스처"
  범위를 벗어나 브라우저가 팝업으로 차단하는 경우가 있었다(시험문제 생성,
  가상질문 생성 둘 다 겪음).
- **해결**: 옵션 모달을 닫으면 곧바로 결과 모달을 띄우고(경과시간 표시하며
  생성) 완료 시 자동으로 새 탭을 시도하되, 모달 하단에 [닫기]/[다시 생성]/
  [새 탭에서 보기] 버튼을 항상 남겨 차단됐을 때도 진짜 사용자 클릭
  (`reopenExamResultWindow()` 등)으로 다시 열 수 있게 함.

### 4.6 Cloud Run 모노레포 배포 경로 문제
- **문제 1**: 저장소가 `ai-server` 외에도 여러 GAS 프로젝트 폴더가 함께 있는
  모노레포라, 빌드 소스 디렉터리가 저장소 루트를 보고 있어 `Dockerfile`을
  못 찾아 빌드가 실패했다.
- **해결 1**: 트리거의 Dockerfile 디렉터리를 `ai-server`로 지정.
- **문제 2**: "Dockerfile" 빌드 유형은 이미지를 Artifact Registry에 빌드+푸시
  까지만 하고 Cloud Run 배포 단계가 빠져 있어, 빌드가 성공해도 새 리비전이
  자동으로 생기지 않았다(서비스 URL이 계속 숨겨짐).
- **해결 2**: 빌드·푸시·`gcloud run deploy`를 전부 명시하는
  `ai-server/cloudbuild.yaml`을 작성하고, 트리거 유형을 "Cloud Build 구성
  파일"로 변경. 이후 GitHub main 브랜치 push만으로 빌드~배포까지 자동화됨.

### 4.7 AI 응답 파싱 — content가 문자열이 아니라 리스트로 오는 경우
- **문제**: Responses API로 웹검색 도구를 쓰면 `AIMessage.content`가 문자열이
  아니라 텍스트 블록과 검색 결과 블록이 섞인 **리스트**로 오는 경우가
  있는데, 코드가 문자열이라고만 가정하고 `.strip()`을 호출해
  `AttributeError`로 500 에러가 발생했다.
- **해결**: `_extract_text_content()` 헬퍼를 추가해 문자열/리스트 두 형태를
  모두 안전하게 처리하도록 정규화.

### 4.8 레이트리밋(TPM 초과)
- **문제**: 강의자료 평가에서 핵심 평가 호출이 슬라이드 전체 텍스트로 이미
  토큰을 쓴 직후, 웹검색 호출도 같은 전체 텍스트를 또 보내면서 조직의 분당
  토큰 한도(TPM)를 초과해 `RateLimitError(429)`가 발생했다.
- **해결**: (1) 웹검색 단계의 입력을 슬라이드 전체 텍스트 대신 이미 만들어진
  짧은 요약(`structure_review`)으로 교체해 토큰 사용량 자체를 줄이고,
  (2) 짧게 대기 후 1회 재시도하는 로직을 추가. 이 TPM 한도는 gpt-4o를 쓰는
  모든 기능이 조직 단위로 공유하므로, 다른 기능에서도 유사 문제가 재발하면
  같은 패턴 적용을 검토 중.

### 4.9 부가 기능 실패가 핵심 기능까지 끌고 내려가는 문제
- **문제**: 강의자료 평가에서 "AI 추가 의견"(웹검색)은 완전 부가 기능인데,
  이 부분의 예외가 안 잡혀서 요청 전체가 500으로 죽고, 이미 만들어진 핵심
  평가(근거 명시·구조 검토 등)까지 통째로 날아간 적이 있었다.
- **해결**: `_generate_currency_review()` 내부 로직 전체를 최상위
  try/except로 감싸 "안쪽에서 어떤 오류가 나든(아직 겪어보지 못한 새 오류
  포함) 예외를 절대 던지지 않고 항상 None으로 수렴"하도록 구조적으로 보장.
  이후로는 웹검색 쪽에서 새 오류가 나도 개별 패치 없이 "그 섹션만 조용히
  빠짐"으로 자동 처리됨. → CLAUDE.md 개발 규칙 10("AI 실패는 항상 화면에서
  흡수")을 코드 구조 차원에서 재확인한 사례.

### 4.10 웹검색 도구 사용 시 스타일 지시(언어·형식)가 안 지켜지는 문제
- **문제**: 웹검색 도구를 쓰는 호출 안에 "한국어로 작성", "마크다운 링크
  금지", "목록 대신 요약 문단으로" 같은 스타일 지시를 함께 넣어도 잘
  지켜지지 않았다(검색 결과 언어 그대로 영어로 답하거나, 원문을 그대로
  글머리 기호 목록으로 인용).
- **해결**: 한 호출로 검색+정리를 다 시키는 대신 **2단계로 분리**: ①
  웹검색 도구로 원시 조사 결과만 받기(언어·형식 신경 안 씀) → ② 도구 없는
  일반 호출로 그 원시 결과를 한국어 요약 의견으로 재작성(순수 지시 따르기
  호출이라 스타일 지시가 안정적으로 지켜짐). 안전망으로 마크다운 링크
  패턴을 정규식으로 한 번 더 제거.

### 4.11 AI 응답의 hallucination(지어내기) 문제
- **문제**: 의견 요약 기능 초기 테스트에서, 무의미한 입력에도 긍정적인
  분위기로 지어내거나, 답변을 개조식으로 그대로 나열하거나, 응답 건수를
  잘못 세거나, 팽팽한 의견을 "대부분"으로 과장하는(또는 반대로 뚜렷한
  다수를 "판단 어려움"으로 얼버무리는) 문제가 반복적으로 발견됐다.
- **해결**: 프롬프트에 grounding 규칙을 명시적으로 추가 — 답변에 없는 내용은
  절대 지어내지 않는다, 해석 불가능한 답변만 있으면 그대로 보고한다, 구체적
  숫자를 언급하지 않고 "대부분/다수/가장 많이 나온 의견/의견이 갈렸다/소수
  의견"의 4단계 비율 기준으로만 판단한다. 같은 패턴(질문 없음도 정상 결과로
  취급, 근거 없는 추측 금지)을 가상질문 생성·강의자료 평가에도 동일하게
  재적용. 또한 `gpt-4o-mini`는 같은 grounding 규칙을 줘도 hallucination이
  잦아 상위 모델(`gpt-4o`)로 교체.

### 4.12 뷰어 접속 불가 — 다중 계정 로그인 환경 (플랫폼 제약, 미해결)
- **현상**: 모바일/태블릿에서 구글 계정 2개(사내 계정 + 외부 계정)가 동시
  로그인돼 있으면 시스템 A(공개 뷰어) 접속이 막히는 경우가 있다(대시보드는
  영향 없음). **단일 계정 로그인 또는 무로그인 상태는 항상 정상 접속된다.**
- **원인**: Apps Script 자체의 알려진 제약이다. 여러 구글 계정이 동시
  로그인된 브라우저에서 `script.google.com/macros/.../exec` 요청 시 계정
  컨텍스트가 충돌한다(`ANYONE_ANONYMOUS` 설정 여부와 무관, 코드 문제 아님).
  exec URL에 `/a/gmail.com/`을 끼워 넣는 커뮤니티 우회법은 실기기 검증에서
  효과가 없어 채택하지 않았다.
- **대응**: 실제 수강생은 대부분 단일 계정이거나 로그인하지 않은 상태라
  서비스 영향이 없다고 판단해, 코드 수정 없이 알려진 제약으로 문서화하고
  넘어갔다. 관리자·직원 기기에서만 재현되며 같은 조건에서도 기기·계정마다
  결과가 갈린다(계정 권한 등급은 원인이 아닌 것으로 확인됐고, 브라우저
  세션·쿠키 이력 쪽이 원인일 가능성이 남아 있다).
